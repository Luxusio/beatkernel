# Native runtime boundaries

The user requires native capabilities to be abstracted as far as their actual semantics allow. Gameplay, replay/judgment, multiplayer protocol, screen lifecycle and playback scheduling policy belong in shared runtime code. Operating-system modules provide device ownership/operations, normalized clocks, native acquisition and required cleanup. An OS entry point must not contain an independent multiplayer implementation or repeat the playback-start state machine. Native evidence and limitations remain explicit; abstraction must preserve clock domains, native reading quality, bounded intervals, provenance, callback constraints and failure semantics. Unsupported capabilities are reported rather than replaced with invented observations. No additional crates are required merely to establish these boundaries.

The first migration makes native_start::start_committed the single owner of silent-device startup, bounded calibration, early agreement, session/host bracketing, observed-slope physical-frame projection, exact arming, actual presentation crossing and cancellation/deadline policy. NativeStartDevice exposes only start, bounded acquisition service, normalized observation with original evidence, actual render report/buffer extent and native host sampling. NativeStartAgreement adapts the existing shared LiveCompetition protocol; fake adapters exercise the same owner using an actual gated mixer. ALSA/CoreAudio provide normalized pairs; WASAPI retains its exact accepted snapshot and physical native origin. ASIO requires a bounded-interval adapter before claiming equivalent frame startup.

This migration does not claim all platform code is already thin. Solo and local-cohort gameplay now each have a shared owner; setup/discovery and some resource/recording glue still reside in native entry points. Continue moving shared decisions and sequencing into common components, leaving the unavoidable native calls and resource ownership behind adapters. Preserve bottom-up component construction, one application crate, retained UI and deterministic shared judging/replay. Compiling native adapters is not physical runtime acceptance.

Future presentation coordinates are native capability semantics that the shared owner must handle uniformly. Retain the first qualifying crossing evidence and service acquisition/status/BGM until actual normalized native host time reaches its playback origin. Keep the same deadline and cancellation handling; host-domain/regression errors reject. Do not publish readiness or shift the saved crossing merely because native metadata describes a buffer's future presentation.

Performance remains part of the boundary. Use generic device traits/static dispatch for shared owner paths where practical, reserve startup acquisition storage before use, and keep device waits, clock sampling, locks and allocation out of the audio callback. Abstraction does not imply per-note signals or per-event object allocation. Error boxing on the control owner does not move policy or allocation into real-time rendering.

The second migration places the complete solo gameplay pump in native_gameplay::run_gameplay. NativeGameplayDevice retains only native observation, host sampling, bounded acquisition, end evidence and observation-source reseeding. Shared code owns pause/resume/input admission/watermark/judgment/capture/competition/completion sequencing. The parsed advance lag applies across platforms, and native source identity survives resume. Native setup/discovery remain subsequent migration work; local-cohort loops use the shared owner described below.

The local-cohort migration uses native_cohort::run_cohort over the existing RuntimeGroup and InputMerger. It reuses NativeGameplayDevice, preserving native buffer/end/clock capabilities. Windows solo and cohort sessions use the same Raw Input/output adapter, with a selected attachment slice and original WASAPI snapshot reseeding. Linux adapters retain fair bounded sweeps across evdev owners; macOS retains IOHID health and exact attachment checks. Shared policy owns admission during pending acknowledgements, deterministic merged ordering, one lag frontier, pause-prefix commits, release reconciliation, partial-report capture and actual all-member completion. Per-player configuration, activation and replay saving now use the common composition described below. Chart loading and audio construction use the shared owners described below; publication placement and native cleanup operations remain explicit composition boundaries.

Default preparation now has one owner in native_defaults::prepare for both live play and replay watching. It plans required metadata queries after strict application syntax validation and preserves explicit options. auto_native supplies OS default identity, actual output format, keyboard candidates and explicitly requested ASIO replay format operations. Keyboard selection policy and metadata admission bounds are shared; the adapter preserves native IDs and ordering evidence. The SettingsHost branches describe option-schema/capability differences without duplicating preparation sequencing in OS entry points. Native stream setup and ASIO interval-aware committed startup remain subsequent work; local member construction is shared as described below.

Local member composition now belongs to native_cohort_setup: one admitted roster creates exact-device bindings, isolated judges and sound voices, captures, record opponents and full/finite completion metadata. The same owner activates RuntimeGroup and InputMerger from the actual calibrated origin. Native adapters still resolve attachments and negotiate/own streams. After their output stop/join and input close attempts, common finalization matches recording destinations by PlayerId, finishes every opponent and attempts every unambiguous save while preserving session/cleanup/save failures. The create-new capture helper is shared by solo and cohort callers. Chart preparation uses the shared owner below; native calibration evidence and remaining resource composition retain their respective operations. This migration does not establish ASIO interval startup or physical acceptance.

Native audio construction now has one owner in native_audio::prepare_audio. It derives the exact bank format, maps section BGM to the declared output/preroll grid, reserves1024 command slots for live work and creates the existing finite/gated mixer. Each native caller supplies its actual rendering bound: ALSA period, CoreAudio buffer or the Windows callback hard bound. Supported solo network modes select initial gating; local sessions and the current ASIO path remain ungated. native_audio::feed_rendered owns checked logical-playback cursor replenishment for both startup and gameplay, ignoring absent/paused reports and retaining256-command work bounds. Native negotiation, calibration evidence and remaining resource ownership still require their respective operations; chart preparation is shared below. The common helper does not create ASIO timing evidence or physical acceptance.

Native chart preparation now belongs to native_chart::prepare_chart. One owner forwards the original path, actual output format, seed, channel policy and PCM limits into the existing loader and section preparer, then checks only retained note lanes for binding coverage. Negative starts reject before file access. Binding failures now precede completion/warning reporting; no other native resource or publication ordering changes. Keep publication separate through the existing player::publish_native_chart owner: Windows solo selects input first, Linux solo builds bindings first, and macOS solo/local publishes before opening input. This preserves attached-only BGA preparation and headless behavior. The helper returns original-song coordinates and section/PCM tail evidence without inventing another clock, player state or native operation. Shared judging/capture preparation is described below. Remaining resource composition and ASIO bounded-interval startup remain subsequent work; physical acceptance stays deferred.

Native judging/capture configuration now belongs to native_judge. NativeJudgeConfig prepares the exact grade-one profile and optional full-song completion; capture_limits and prepare_capture retain the existing bounded recording format and pristine-judge checks. JudgeEngine itself was already shared, so no additional constructor wrapper is needed. These operations remain separately callable: solo completion precedes publication, profile creation follows publication/cancellation, and capture remains inside the outcome closure after native owners open. Cohorts prepare one profile, clone it for independent judges, and finish pure member setup before opponent loading. Finite completion and disabled recording skip their unused validation paths. Device selectors, original solo voices, cohort voice partitions, recording paths, competition APIs and native cleanup retain their existing owners. Abstraction does not merge solo and cohort capabilities or change replay bytes. Native resource composition, solo finalization and ASIO interval-aware startup remain subsequent work.
