# Common Runtime touch routing

Opt-in spatial touch routing enters the existing Runtime judge, sound, telemetry
and report path after clock/sequence/chronology/end validation. Configured
touches select one destination or remain unbound; unconfigured input retains
ordinary BindingMap behavior. Separate projected coordinates choose a region
without changing the physical sample.

Routing refusals precede acquisition adoption. Judge/audio failures after
admission preserve committed state and report evidence. Solo and local cohorts
share the same execution rather than introduce platform-specific judging.

A routing checkpoint can be copied fallibly with its full contact capacity.
Fresh replacement clears contact ownership; explicit replacement accepts a
coherent judge/transport/router checkpoint supplied by the caller. Audio
synchronization and checkpoint pairing remain caller responsibilities.

StepGameplay and the Rust BrowserGame binding expose preparation-time touch
region configuration and projected physical input. Browser region rows reuse
the common identity representation and validate their prepared-lane destinations.
Window/Worker touch acquisition, presentation feedback, record catalog migration
and HID handling remain further work.

Ten portable fixture groups are authored: six core Runtime groups and four
application setup/cohort/StepGameplay groups. They include actual Mixer output,
paired contact restoration and typed replay reconstruction. Workspace all-targets,
headless all-targets, WASM browser and WASM browser-audio cargo check each exited
0. WASM retains the existing three cadence dead-code warnings. Checks compile
fixtures without executing assertions; browser/device execution remains deferred.
No runtime acceptance or measured performance claim is made.
