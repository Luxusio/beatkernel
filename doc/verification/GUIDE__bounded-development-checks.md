# 개발 중 검증 비용 줄이기

수정한 계층의 실제 동작을 먼저 검사하고, 통합 이후 전체 회귀검사를 수행한다.
전체 검사와 독립 review/QA를 생략하는 지침이 아니다. 실제 브라우저·장치·
외국 OS 실행을 순수 fixture나 타입 검사로 대신 완료 처리하지 않는다.

- source/test writer가 관련 파일을 동결한 후 컴파일한다. coordinator 한 명이
  컴파일 프로세스를 소유하고, 서로 다른 Cargo 프로세스로 중복 빌드하지 않는다.
- 순수 계층은 필요한 package·`--lib`·test target으로 시작한다. 실제 CLI 검사에
  필요한 실행 파일은 해당 검사 때 빌드한다. GUI·추가 transport feature는
  그 변경의 증거에 필요한 경우 활성화한다.
- 전체 또는 여러 test target의 회귀검사는 `--no-fail-fast`로 실패를 한 번에
  수집한다. 수정하지 않은 성공한 좁은 검사를 이유 없이 반복하지 않는다.
- test filter가 실제 실행한 개수를 확인한다. 0 tests는 PASS 근거가 아니다.
  VM fixture를 쓰는 Node 검사는 `--experimental-vm-modules`가 필요하다.
- 같은 source의 빌드·bindings를 export 검사와 브라우저 검사에서 재사용한다.
  main/audio WASM은 각각 빌드 직후 bindings를 생성한다. source가 바뀌면
  해당 산출물을 다시 만든다. 오래된 산출물로 최신 소스를 검증했다고 주장하지 않는다.
- 하나의 Cargo 내부 병렬도는 메모리와 활성 프로세스를 확인한 뒤 정한다.
  이 환경의 확인 시점에는 물리 RAM 약 30 GiB, available 약 12.8 GiB였다.
  다음 관련 빌드는 `CARGO_BUILD_JOBS=2`를 사용하고, 메모리 압박이 보이면
  1로 낮춘다. 고정된 다른 기기의 안전 한도나 빌드 가속 보장은 아니다.
- Rust 컴파일과 독립 Node/읽기 검사는 병렬 실행할 수 있다. 실제 browser
  기능 검사는 가능하지만 성능 측정은 경쟁 부하와 분리한다.

2026-10-12 관측: 실제 앱 CLI 포함 첫 빌드 4분 47초, 수정 후 같은 범위의
캐시 빌드 41.57초. 코어 전체 재검사의 빌드는 7.71초였고 547개가 통과했다.
이 수치는 해당 checkout의 관측이며 다른 빌드의 시간 예측이 아니다.
